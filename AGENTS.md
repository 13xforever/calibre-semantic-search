# AGENTS.md

calibre **GUI plugin** (not a standalone app): meaning-based search + LLM-extracted book attributes. No build system, no package manifest (the ZIP ships exactly `src/`; dev dependencies live in `requirements-dev.txt` and are never shipped), no typechecker — verification is ruff (pyflakes + isort rules) + `py_compile` + the stdlib unittest suite.

## Environment (new system)

- Dev environment is a project-local **`.venv`**: `python dev.py setup` creates it from the closest installed Python to what calibre ships — highest version in **3.12..3.14** (found via the `py` launcher; calibre 9.14's Windows build runs CPython 3.14.7, and staying at or below that is the safe direction) — then pip-installs any missing dev dependencies into it. Re-running reuses the existing venv and installs only what's missing (a no-op when complete). Nothing is installed system-wide; setup does NOT run the gate.
- Dev dependencies (`requirements-dev.txt`): `ruff` (lint step), `lancedb` (hard test dependency), `lxml==6.1.1` (the exact version calibre 9.14 bundles — the chunker's HTML walk runs against it in tests too; keep the pin in sync when calibre updates it), `numpy` (optional at runtime with a pure-Python fallback, but required in the test env to exercise the numpy paths — see `TestNumpyFallbackEquivalence`; calibre does not bundle it), `zstandard` (zstd codec — without it fresh stores use zlib). The store reads lancedb results via `.to_list()`, never pandas: calibre ships no pandas, so any pandas use would break the lancedb backend at runtime.
- Run the gate through the venv interpreter: `.venv\Scripts\python dev.py` (or activate `.venv`). The code uses nothing newer than Python 3.9, so any of 3.12..3.14 works.
- Hard non-stdlib dependency: **lxml** (calibre bundles it). **numpy is optional and user-installed**: there is no background auto-install anywhere — the settings *Dependencies* tab (`config_widget.py`) has explicit Install/Uninstall buttons that call the `utils.install_*`/`uninstall_*` pip helpers in a worker thread. Without numpy the sqlite backend falls back to pure-Python vector math (~36x slower search), so it's performance-critical even though not required. store.py caches the numpy import at module level, so a fresh install needs a calibre restart to take effect (the status line says so). None of the dev deps are shipped; lancedb/zstandard/numpy are optional at runtime.

## Commands (run from repo root, via the venv interpreter — `.venv\Scripts\python dev.py ...`)

- Provision a new system (create/refresh .venv, install missing dev deps — no tests): `python dev.py setup`
- Full gate — compile + lint + test + build, stop on first failure: `python dev.py`
- Compile check (byte-compiles `src/` + `tests/`): `python dev.py compile`
- Lint (ruff, pyflakes + isort rules — real bugs and consistent import order, nothing else; config in `ruff.toml`; needs `pip install ruff`, a missing tool fails the gate loudly like lancedb): `python dev.py lint`
- Tests (all): `python dev.py test` (equivalent to `python -m unittest discover -s tests`)
- One file: `python -m unittest discover -s tests -p "test_store.py"`
- Build the installable ZIP: `python dev.py build` — the ZIP **mirrors `src/`**: `__init__.py`, the other modules, and the import-name `.txt` at the ZIP root (calibre's loader requires them there), assets under `assets/`. The script reopens the ZIP and verifies the entry set afterwards.

**After any change to a shipped file**: run `python dev.py` so the tests pass and `semantic_search.zip` always matches the working tree. Don't hand off a task with failing tests or a stale ZIP.

## Testing gotchas (easy to get wrong)

- `tests/` is **not** a package (no `__init__.py`). `python -m unittest tests.test_x` fails — always use `discover -s tests [-p file]`.
- Plugin source lives in `src/` (the ZIP mirrors it; see Commands). Modules are loaded in tests via `tests/util.py:load(name)` (by filename from `src/`, no package). That only works for self-contained modules (`chunker`, `utils`, `attributes`, `embed_client`). `store.py` imports its migration steps from the `migrations/` subpackage, so `test_store.py` uses the `_loadpkg` pattern too.
- `indexer.py` and `gui.py` use **relative imports** (`from .store import ...`), so they can't be loaded with the plain helper. Load them as a synthetic package — see the `_loadpkg` pattern in `tests/test_indexer.py`. Copy that approach for new indexer/gui tests.
- The LLM/embedding paths are tested with fakes (no network). `calibre.*` imports are unavailable in the test interpreter, so any `calibre.ai` / `calibre.db` import must stay **inside functions** (lazy), never at module top level — a top-level calibre import breaks the whole suite.
- The lancedb backend tests (`test_store.TestVectorStoreLance`, `test_db_lifecycle.TestLanceDb`) are **not skipped**: `lancedb` is a hard test dependency (`pip install lancedb`). The suite must exercise that code path even though most users run the sqlite backend — without the package the tests fail loudly with the install error, which is intentional; don't wrap them in `skipUnless`.
- Simulating a *missing* optional package in tests means patching `store._module_available` (the real module stays importable — that mirrors an in-session uninstall, where the already-loaded module still works while fresh opens must block). See `test_db_lifecycle.TestBlockedStates` / `TestCodecRecompress`.

## Architecture (not obvious from filenames)

- Entry chain: `__init__.py` (`SemanticSearch`, `InterfaceActionBase`) → `actual_plugin = 'calibre_plugins.semantic_search.gui:SemanticSearchAction'`. Real GUI lives in `gui.py`; installed as `calibre_plugins/semantic_search/...`.
- **Asset loading** (`gui._plugin_icon`, `store._load_default_dict`): assets ship in an `assets/` subfolder next to the package. Installed plugins load from the ZIP via calibre's custom loader with a *virtual* `__file__` — filesystem lookups never work there — so both accessors try the injected zip-aware `get_icons`/`get_resources` first and fall back to a plain file when running from source. Don't "simplify" this to a filesystem-only path; that silently breaks installed mode (`_load_default_dict` would crash whenever zstandard is present).
- **Two-model pipeline** in `indexer.py`: the worker drains the embedding (dirty) queue first, then runs an attribute-extraction phase — deliberately batched so the two models aren't swapped mid-run. Attributes run automatically after indexing (`auto_extract_attributes`, default on) or via the "Extract attributes…" menu. Failed books are recorded in the `attr_failed` meta key and excluded from re-runs until retried.
- **Attribute storage source of truth is the store's `attrs_raw` table** (`store.set_attrs`/`get_attrs`). Calibre custom columns are a *best-effort mirror* only — runtime custom-column creation in calibre's newAPI isn't reliably usable for an immediate `set_field`, so don't "fix" things by writing columns alone.
- Adding a setting touches **three** places: the dataclass in `utils.py` (`Settings`), the key list in `_settings_from_dict`, and the collect method in `config_widget.py`. Settings persist under gprefs key `semantic_search_settings` (`utils.PREF_KEY`).
- **Store schema v2** (`store.py`, versioned via `PRAGMA user_version`; migrations in the `migrations/` subpackage, one self-contained file per version step — `v1.py` brings the meta tables to their current shape and runs on open, `v2.py` migrates the chunk tables and runs deferred): per-model chunk tables `chunks_<normalized_model>` holding slim rows `(id, book_id, chunk_no, text_z, chapter_path, vector)` — chunk text is compressed with the codec recorded in meta key `text_codec` (zstd L3 + bundled `default_compression_dict.bin`, zlib fallback). Legacy v0 DBs migrate on open: meta migration (registries, integer-second timestamps, `file_info` table from `meta['fileinfo:<id>']`) runs in the constructor; the heavy chunk work (split single `chunks` table into per-model tables, then slim each) is **deferred** to `VectorStore.finalize_schema()`, driven by `needs_finalize()` and run in a background thread by `gui._start_for_library` before indexing starts. Both steps are resumable (per-group commits, keyset staging with `MAX(id)` resume point). During finalize the WAL auto-checkpoint is disabled and the WAL is checkpointed explicitly (`PRAGMA wal_checkpoint(TRUNCATE)`) at phase boundaries — after split, after each slimmed table, and after the final VACUUM (which in WAL mode leaves the rebuilt DB in the WAL while the store stays open): with a multi-GB WAL the default in-commit passive checkpoint can stall for minutes on slow storage. **When a new migration step is added (a sqlite `migrations/vN.py` or a lancedb equivalent), update `tests/test_db_lifecycle.py`**: it builds small reproducible DBs per scenario (legacy v0 migrated to latest, fresh sqlite at latest, lancedb) and runs the same full operation suite on each — the new step must be covered there too.
- **Per-library vector backend** (`store.py`): the backend is a *per-library* choice stored in meta key `vector_backend` of each library's DB; the global `Settings.vector_backend` is only the default for brand-new libraries (legacy value `'auto'` coerced to `'sqlite'`). Two open libraries may use different backends at once. A backend switch and a codec change are just more finalize stages: `VectorStore.pending_stages()` returns the ordered list (`'schema'`, `'backend'`, `'codec'`) and `finalize_schema(progress)` runs them — same background-thread-before-indexing path as schema v2, with per-model resumable progress in meta keys `backend_migrate`/`recompress`. Backend migration moves books model-by-model into the destination backend (reusing `insert_chunks` via a `_MigrateRow` shim), writes an in-flight marker **before** the first row moves (crash-resumable; on resume the store reopens on whichever side already holds data and continues from `books_done`), flips `vector_backend` and drops the source storage only at the end. Orphaned storage left by an abandoned switch is swept on open — but *only* when no in-flight marker exists, so a crash mid-transfer never loses the not-yet-moved side. The lancedb backend stores plain text (no codec); zstd/zlib compression is sqlite-only, and its recompress (`'codec'` stage) is an in-place per-row rewrite keyed on magic bytes — no staging table, idempotent, resumable.
- **Per-library chunk compression** (`store.py`, mirrors the backend choice): meta key `text_codec` records the codec the chunks are *actually stored with* (zstd L3 + bundled dict, or zlib) — it is the source of truth, there is no separate "choice" key. A switch confirmed in settings is recorded as a `recompress` marker (JSON progress, `store.recompress_marker`) that `finalize_schema()` executes as an in-place per-row rewrite keyed on magic bytes (no staging table, idempotent, resumable); the `'codec'` stage is pending exactly while the marker exists and it is deleted when the conversion finishes. `store.write_codec_choice(meta, codec)` is what settings confirm calls: with sqlite chunk data present it writes the marker, without it it updates the `text_codec` spec directly so data that will arrive uses the chosen codec. `ensure_codec_setup()` runs on every open and self-heals an unusable record (zstd without zstandard — only reachable for dataless libraries, since stored zstd data blocks the open instead) to a usable codec, so a fresh/dataless library never blocks on the package. The dialog's compression combo edits the stored codec (`VectorStore.stored_codec()`; for a dataless library it shows what a fresh one would use — zstd while zstandard is importable, zlib otherwise) and is enabled only with a library context + sqlite backend + zstandard importable + not blocked-with-data. Installing zstandard does NOT auto-convert: a zlib library stays zlib until the user switches in the dialog.
- **Dependency pre-flight** (`store.MissingDependencyError`): opening a store whose *stored data* needs a missing package raises `MissingDependencyError(dep, has_data, want_backend)` instead of failing mid-query — for sqlite that means chunk tables exist AND the recorded codec is zstd AND zstandard is missing (the has-chunks guard is what keeps dataless libraries unblocked), plus an in-flight `recompress` marker targeting zstd without the package; for lancedb, data present without the package. A pending switch *to* an unavailable backend does not block the open — only where the data actually is matters; the migration then fails with the same error when attempted. The GUI (`gui.py`) catches it into a blocked state: status lines explain what's missing, search/indexing/attributes are disabled, and the library's backend/compression combos in settings are locked while `has_data`. `action.on_dependency_changed` only rebinds numpy now — zstandard needs no in-session reaction (a blocked store was never open; it reopens normally once the package is back), and confirming the settings dialog retries `_start_for_library()` while still blocked, so a just-installed package unblocks the library without switching libraries.
- **Dependencies tab** (`config_widget.py`): explicit Install/Uninstall buttons for numpy/zstandard/lancedb, each running the matching `utils.install_*`/`uninstall_*` pip helper in a `_DepWorker` thread and reporting via a status line. There is no background auto-install anywhere (the old `gui._ensure_numpy` was removed). Uninstalling numpy just degrades sqlite search to pure-Python math until calibre restarts. Two uninstall gates keep a library from being left blocked by its own settings dialog (both key on the *stored* state, not the combo text): the lancedb button is disabled while lancedb is selected as the vector backend, and the zstandard button is disabled while this library's chunks are stored as zstd — switching to zlib in the dialog (and confirming) re-enables it. The per-library storage choices themselves live in the *Indexing* tab (backend + chunk-compression combos, seeded from the open/blocked store or from availability); confirming the dialog writes `vector_backend` and/or the codec marker/spec via `write_codec_choice`, reopens the library so any pending migration/recompress runs in the background before indexing starts, and retries the open if the library was blocked.

## Gotchas

- **Never delete files outside the scratch dir** (`%TEMP%\opencode`) without asking first — including test/benchmark artifacts like migrated DB copies on other drives. Cleaning up the scratch dir is fine; anything else needs explicit permission.
- **Benchmark with real parameters, never invented ones**: the target embedding dim is **4096** (the model this plugin is aimed at). Any perf/memory estimate (numpy vs pure-Python scoring, RAM-budget batch sizes, storage) must use that dim and realistic chunk counts — results scale linearly with dim, so a made-up dim produces wrong conclusions.
- Use **binary units** for all computer measurements: kB/MB/GB mean powers of 1024 (1 kB = 1024 B, same as KiB; 1 MB = 1024 kB, ...). Powers of ten are confusing in programming contexts — don't use them for byte counts.
- The store opens SQLite with `journal_mode=WAL` (`store.py`). Inspecting `semantic-search.db` directly can show **stale/empty tables** (rows live in `-wal` until a checkpoint). Don't "debug" persistence by eyeballing the raw file — verify via the store API or the *Index status* dialog's `Attributes stored: X/Y books` line.
- In WAL mode `PRAGMA auto_vacuum=INCREMENTAL` only takes effect **through a finished `VACUUM`** — setting it on its own does not persist (it reads back 0). That's why new DBs and migrations end with the pair `PRAGMA auto_vacuum=INCREMENTAL; VACUUM;`, and why `needs_finalize()` treats `auto_vacuum != 2` on an otherwise-v2 DB as "previous VACUUM never completed" and re-runs it.
- **File mtimes are truncated to integer seconds, never rounded** (migration `migrations/v1.py`, runtime `indexer._mtime_to_int`). Rounding up would store a mtime later than the file's real one, so change detection would see every book as modified.
- **Calibre's in-place plugin reload does NOT re-import submodules** (`calibre/customize/zipplugin.py`): Preferences → Plugins re-runs only the package `__init__.py` via `importlib.reload`; already-loaded submodules stay cached in `sys.modules`. Consequences: (a) editing a submodule like `utils.py` is **not** picked up by a reload — replace the installed `...\calibre\plugins\<name>.zip` and **restart calibre** for it to take effect; (b) never do a hard top-level `from .submodule import name` in `__init__.py` for anything that can be absent/stale — on a reload with a stale submodule it raises `ImportError` and crashes the whole plugin load (the action vanishes, calibre logs an unhandled exception). Import the module (`from . import x`) and guard the attribute with `getattr`, so a stale/partial install degrades gracefully instead of crashing (see `_bootstrap_external_deps` in `__init__.py`).
- The plugin targets calibre 9.x dev and uses `calibre.ai` structured-output + newAPI internals. A local checkout of the calibre source tree is useful for reading those APIs (plugin loading in `calibre/customize/zipplugin.py`, action plumbing in `calibre/gui2/actions/__init__.py`); the plugin itself ships only what `src/` contains — that's exactly what `dev.py build` stages into the ZIP.
